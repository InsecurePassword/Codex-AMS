# AMS Daybreak Blue cyber fallback

Read only after an explicit cyber-safeguard refusal from a standard Sol worker or delegated manager for one still-required authorized defensive unit. Daybreak Blue is never proactive or normal routing.

## Trigger and frozen unit

Use `ams_daybreak_blue_max` only when all are true:

1. the work is lawful, explicitly authorized defensive cybersecurity work on systems, code, artifacts, accounts, networks, or data the user owns, operates, or is authorized to analyze;
2. a real standard-Sol work order explicitly refused or blocked the unchanged work because of cyber safeguards;
3. the refusal is not weak output, ordinary inability, timeout, transport/capacity failure, missing context/tool, permission/sandbox denial, account/quota failure, or a non-cyber refusal;
4. the objective, target, scope, exclusions, authorization basis, dependencies, data boundary, and operational boundary can remain frozen;
5. no higher-priority safety, project-native, ownership, approval, or Trusted Access boundary independently blocks the work.

Daybreak Blue is worker-only. It grants no permission, target authority, credential access, retention change, or offensive authorization. It never changes to another model or specialized route, broadens into an offensive workflow, creates another Daybreak unit, or escalates to root execution.

Keep only root-session state; use project-native continuity or a concise handoff. Create no AMS database, receipt history, lock, campaign, transcript, or recovery file.

```text
Fallback unit ID / Root objective ID:
State: eligible | preflight | active | consumed | blocked
Refusal source: work-order
Original Sol work-order ID: <ID>
Original Sol role: worker | delegated-manager
Logical parent / Refusal evidence:
Scope basis / Dependencies-readiness:
Frozen objective / Target / Scope / Exclusions:
Authorization basis / Data boundary / Operational boundary:
```

A refusal without a real standard-Sol work-order ID and correlated result is ineligible. Root handling without that work order never qualifies. A root whose model is external to AMS must first commission the unchanged unit through a standard Sol profile. Retries, equivalent refusals, replacement, reparenting, compaction, or intensity changes retain the unit. A material boundary change is a new objective routed through standard Sol.

## Stable access boundary and session admission

Separate durable access closure from ephemeral session admission.

### Stable access boundary

Key the boundary by:

```text
Provisioned access path and exact execution surface
Approved identity plus organization/workspace/API-project boundary
Internal-only status
Retention requirement and coverage
```

Record:

```text
Access-boundary ID:
Closure: open | closed-unavailable
Closure evidence / Explicit reopen condition:
```

The key excludes session and profile identity. Closure survives replacement, handoff, recovery, and profile updates. Reopen only after explicit recheck or material new provisioning/access evidence; missing/contradictory continuity fails closed.

If the unchanged unit was blocked before confirmed task start only by this closure, authorized reopen returns it to `eligible`; `active` or `consumed` never resets. A later session or explicit recheck may release a session-only admission block, never a stable closure.

### Ephemeral admission and active-task correlation

For an open boundary create a current-top-level-session admission:

```text
Admission generation:
Admission state: unverified | preflight | verified

Task operation ID / Work-order ID / Nonce / Start attempt:

```

One unit may reserve a boundary. Admission is never reusable across objectives, units, parents, custody, topology, boundaries, or sessions. Before confirmed start, profile change, interruption, compaction, approval wait, handoff/root replacement, login change, or identity/path uncertainty invalidates it, clears reservation/root freeze/allocation, returns the unit to `eligible`, and requires a new generation unless closure or a session block leaves it `blocked`.

A confirmed active task keeps its immutable admission/task correlation through terminal reconciliation, including handoff/root replacement. That admission authorizes no other task.

## Access and route gate

Before preflight establish non-secret evidence for the exact approved route. Do not record credentials or unnecessary personal data.

- `codex-workspace`: use only the named internal Codex/ChatGPT organization or workspace and an explicitly covered Codex surface.
- `api-organization`: use only the named internal API organization/project and an approved API/Codex API workflow.
- `user-or-model-specific`: use only the exact provisioned identity/surface; `none-user-level` is valid only when provisioning explicitly says no organization/workspace/project applies.

Accept platform metadata, official provisioning/onboarding evidence, or direct current user confirmation tied to the active identity/surface. Never combine workspace/API approval; installation, profile/catalog presence, prior success, or no error proves nothing. Missing/contradictory identity, path, surface, internal-only status, or retention fails closed.

The requested alias is `gpt-daybreak-blue`. Accept observed route identity as:

- `gpt-daybreak-blue`; or
- `gpt-5.6-sol` only when the same admission contains direct evidence that execution used the approved Daybreak Blue access path and product surface.

The underlying `gpt-5.6-sol` identity alone never proves Daybreak Blue. Missing identity or any other model is route mismatch and blocks admission without creating durable access closure unless direct boundary evidence separately proves closure.

## Parent custody and ownership

Resolve custody before preflight and record `Custody mode: active-manager | serial-inactive-resumable | superseded`:

- Sol worker refusal: close/supersede it, prove it no longer writes, and preserve its logical parent;
- delegated-manager refusal, including `auto`: choose `active-manager` only when the selected topology and remaining allocation permit a valid child lane; otherwise choose `serial-inactive-resumable`, close the manager at a safe boundary, and run the fallback serially;
- unavailable parent or deliberate flattening: use normal hierarchy supersession/custody transfer.

The refusing parent relinquishes the surface. Before confirmed start the root holds the write freeze; a never-started worker owns nothing. Transfer exact worker ownership only on confirmed start.

After every terminal path—preflight failure, closure, exhausted no-start, cancellation, or task result—resume the inactive manager or supersede it explicitly; relay evidence, reconcile ownership/allocation, and close/continue the subgraph. Never strand it.

### Preflight failure and start budget

Preflight and task dispatch each allow one initial start and only the core same-lane retry after proven no-start. Retry keeps work-order/operation identity, uses a fresh nonce, and increments only start attempt; it is not a replacement and creates no separate budget.

Repeated `spawn_ready` follows `runtime-core.md`. Probe success cannot reset the Daybreak start budget or authorize another profile/surface; probe failure stops process-dependent work.

Close the stable boundary only when direct authoritative entitlement, provisioning, path, retention, or effective-route evidence proves it unavailable or mismatched. Refusal, weak/unexpected/non-distinguishing output, timeout, malformed result, stale admission, profile defect, or runner/no-start exhaustion only invalidates admission and session-blocks the unit unless that direct evidence exists. Every pre-start terminal path clears reservation/root freeze/allocation and restores any inactive parent; uncertain start is active. Do not retry another profile, surface, unit, or parent.

On confirmed start, transfer the exact surface and set the unit `active`. If start is uncertain, treat it as active and prohibit another task.

Every terminal result after confirmed start—complete, partial, blocked, failed, refused, lost, cancelled, or unusable—sets the unit `consumed`. Do not retry, replicate, rotate profiles, reset through reparenting/recovery, or broaden the task.

Conflicting or nonmatching admission/operation/work-order/nonce evidence cannot overwrite active/newer state, reopen closure, restore ownership, or reset a consumed unit. Only direct boundary evidence may close it; task-specific, refusal, or quality failure consumes only the unit.

Daybreak output is evidence, never acceptance. Relay it through the logical parent or superseding custodian, validate under the original objective, release the reservation, and continue the authorized automation queue. If the route cannot proceed, block only the affected unit and continue independent authorized work.
