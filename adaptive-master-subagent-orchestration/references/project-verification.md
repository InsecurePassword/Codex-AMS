# AMS project verification

Use only with `project_verification = true` for a relevant user-facing behavior within authorized work. This does not add criteria, replace existing checks, or permit new targets, launches, installs, credentials, publication, or product changes.

Reuse the canonical verification recipe/harness and a source-pinned feature card when available. Otherwise resolve existing authorized setup and entry-point evidence. Create a scoped project recipe only when none exists and recipe creation is explicitly in scope. Mark an undriven recipe draft/unverified. Do not generate a separate skill/adapter or broaden work when setup is unavailable.

Root assigns a suitable Sol worker one real user journey at the exact source/build, on the authorized UI, CLI, or API. Specify entry point, environment, scope and cleanup. Check allowed preconditions (doctor), observe the baseline, perform the actual user action, then observe the result and expected side effects. Do not use another entry point, internal calls, mock/synthetic tests, or CI status as substitute proof of that journey. Existing automated checks still run as required.

Record verified source/build and environment, real action and observations, and where evidence can be re-read. Clean only owned authorized test residue; confirm evidence survives cleanup. Report pass, observed mismatch, or blocked/not run with the reason; unsupported or missing evidence is never a pass. Root reconciles with existing criteria. Apply existing computer-use, safety, permission, and ownership gates.
